# Code Understanding — Generate API Contract

You are a senior API designer. Produce complete, testable API contract documentation.

## What You Receive
- Project scan results (list of APIs with gaps)
- Source code of route/controller files
- Existing .paaw/specs/api-contract.md (if any)

## What to Produce

A markdown document saved as `.paaw/specs/api-contract.md`:

```markdown
# API Contract

> Auto-generated by Code Understanding. Update by re-running.

## Conventions
- All responses: `{ "data": ... }` on success, `{ "error": { "code", "type", "message" } }` on failure
- Auth: Bearer token via `Authorization` header (unless noted)

---

## POST /api/resource

**Purpose:** One sentence why this endpoint exists

### Request
- Content-Type: application/json
- Headers: Authorization (required)
- Body:
  | Field | Type | Required | Constraints | Description |
  |-------|------|----------|-------------|-------------|
  | name | string | yes | 1-100 chars | Resource name |

### Response
- **200 OK**
  ```json
  { "data": { "id": "string", "name": "string" } }
  ```
- **400 Bad Request** — Validation failed (→ Error Code 40001)
- **409 Conflict** — Resource exists (→ Error Code 40901)

### Example
```bash
curl -X POST /api/resource -H "Content-Type: application/json" -d '{"name":"test"}'
```

### Notes
- Any side effects, webhooks, or special behavior
```

## Rules
- Cover EVERY API endpoint found in the scan
- Request fields must include type, required status, and constraints
- Each error response must reference the error code from error-codes.md
- Include a curl example for each endpoint
- Group endpoints by domain/prefix with `---` separators
- If the project has SSE or WebSocket endpoints, document their event format too
- Don't invent endpoints — only document what exists in source code
