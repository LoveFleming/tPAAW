# 💧 知識蒸餾結果：AI 工具引擎 測試與除錯紀錄

## 1. 任務摘要
* **做了什麼**：對自建的 AI 助理系統（可能名為 PAAW，參考 OpenClaw 架構）進行整合測試。測試了大型語言模型（`glm-5.1`）與內部工具的互動，包含查詢 App 列表、新增筆記、以及執行翻譯與存檔。
* **為什麼做**：驗證 Tool Engine 的穩定性，確保 LLM 能正確觸發 API/工具，而不是僅生成模擬文字，同時檢驗資料庫的讀寫一致性。

## 2. 關鍵決策
* **強制使用真實工具呼叫**：在測試中發現 LLM 會「假裝」呼叫工具並生成擬真的假資料。決策上必須透過 Prompting 或系統設定，強制模型實際執行底層 API（如 `pocket_list`, `pocket_add`），以確保資料真實存入與讀取。

## 3. 技術要點
* **LLM 模型**：使用 `glm-5.1` 作為核心大腦。
* **自定義工具鏈**：
  * `app_list`：查詢系統目前安裝的應用程式。
  * `pocket_add` / `pocket_list`：與「Pocket 筆記系統」互動（支援 `todo`, `idea`, `vocab`, `sentence`, `mood`）。
  * `translate_exec` / `translate_add`：執行多國語言翻譯並將結果（含語源、例句）存回資料庫。
* **Data App 架構**：系統採用標準化的資料應用架構（`dataShape: array`），將不同功能模組化為獨立的 App。

## 4. 遇到的問題與解法
* **🐛 Bug 1：LLM 幻覺導致資料狀態不一致**
  * *問題*：詢問 Pocket 有幾筆資料時，LLM 有時會回報正確數量（如 4 筆），有時卻回報 0 筆。事後 LLM 坦承是「文字模擬」的結果，而非實際呼叫 API。
  * *解法*：在 Prompt 中明確指示「直接用 app_list 工具查」，並要求模型在回覆前顯示真實的工具呼叫日誌（如 `> 🔧 Pocket List ...`）。
* **🐛 Bug 2：UI 顯示 `N/A` (Not Applicable)**
  * *問題*：使用 `pocket_add` 新增 `todo` 類型筆記時，系統提示訊息出現 `🎒 N/A (todo)`。
  * *解法*：診斷出這是 Schema 不匹配的問題。工具回傳格式預設抓取 `title` 欄位，但 `todo` 結構只有 `text` 欄位。**解決方案**：需修改工具回傳格式或 App Schema，針對不同類型動態映射顯示欄位（如 todo 映射 `text`、vocab 映射 `word`）。

## 5. 產出的成果
* **功能驗證**：成功驗證了 App 查詢、筆記新增（含排程提醒如「明早六點運動」）、翻譯與單字收集（如將「和平協議」、「滯留鋒」翻譯並整理 KK音標、語源記憶法）。
* **累積測試數據**：成功在資料庫寫入並讀取真實的 Todo 與 Mood 紀錄。

## 6. 可復用的模式 (Best Practices)
* **防幻覺提示模式**：當要求 AI 查詢資料時，避免使用開放式問句（如「我有幾個 app？」），應直接指定工具：「**使用 `[tool_name]` 工具查詢**」。
* **動態欄位映射**：在設計 NoSQL 或多型態的資料表（如 Pocket 同時存 todo 和 mood）時，前端/回應渲染層應採用策略模式，根據 `type` 動態決定要提取哪個欄位作為 `title` 顯示，避免 `N/A`。
* **複合式工具呼叫**：在實作翻譯功能時，採取「執行 (`translate_exec`) -> 儲存 (`translate_add`)」的兩步走工具設計，能讓 AI 專注於生成高品質內容，再交由另一個工具處理持久化。
