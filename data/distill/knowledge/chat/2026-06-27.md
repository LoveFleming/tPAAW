## 💬 Chat 對話紀錄蒸餾 — 2026-06-27

### 1. 任務摘要
- **做了什麼**：用戶測試其筆記應用程式（Notes app）的「連結開啟筆記」功能。
- **為什麼做**：用戶明確表示「我在測試連結的功能」，目的是驗證透過特定 URL scheme 或錨點連結是否能正確跳轉到特定筆記。

### 2. 關鍵決策
- **決策**：決定還是提供完整的筆記清單與連結。
- **原因**：即使重複收到相同請求（「給我筆記的連結」），用戶最後一次提到「測試」，表示需要穩定的測試材料，而非單純的資訊索取。提供完整清單能確保測試的一致性。

### 3. 技術要點
- **筆記連結格式**：使用標準的查詢參數 URL，而非 RESTful 路徑。
    - `paaw://notes?note=note_mqw5ok05tze7&notebook=default`
    - `#/notes?note=note_xxx&notebook=default`
- **工具使用**：助手透過呼叫 `notes_recent` 工具來獲取筆記列表，這是一種典型的「Read/Query」服務端功能。
- **連結類型**：對話中同時出現了兩種連結格式：
    1.  **App 自定義協議（scheme）**：`paaw://...` 用於直接喚起本地應用程式。
    2.  **前端路由錨點（Hash-based routing）**：`#/notes?note=...` 用於在同一個 Web 應用內部進行頁面跳轉，不觸發伺服器請求。

### 4. 遇到的問題與解法
- **問題**：用戶連續三次要求「給我筆記的連結」，顯示對第一次回應不滿或無法正常使用。
- **解法**：助手在第二次與第三次回應時，調整了連結格式：
    - **從** `paaw://notes?note=XXX`（App 專用協議，可能在網頁環境無法直接點擊或瀏覽器不支援）。
    - **改為** `#/notes?note=XXX`（標準 Web 錨點連結，通用性更高）。這個轉變解決了用戶在測試時可能遇到的「連結無法點擊」或「跳轉失敗」問題。

### 5. 產出的成果
- **測試素材**：提供了兩筆筆記的完整連結，作為測試案例。
- **路徑記錄**：成功記錄了不同連結格式的差異與潛在的相容性問題。

### 6. 可復用的模式
- **測試引導**：當用戶重複請求相同資訊時，主動詢問目的（「需要看內容或建立新筆記嗎？」）可以更快釐清需求（是測試？還是忘記了？）。
- **連結降級策略**：當高階的 App 協議（`paaw://`）可能失效時，應準備一個備用方案（Web 錨點 `#/notes`），以確保連結在不同平台（Web / Mobile / Desktop）都能正常工作。
- **URL 設計原則**：使用查詢參數（`?note=xxx&notebook=default`）比使用路徑參數（`/notes/default/xxx`）更靈活，易於擴展（例如未來加入 `action=edit` 等參數）。
