# F20261016-010 — Agent 執行日誌與日誌保留政策

> 功能文件 · Feature: [F20261016-010](../.paaw/features/FEATURES.json)
> 對應程式碼：`packages/server/src/routes/agent-logs.mjs`、`packages/server/src/routes/log-retention.mjs`、`packages/server/src/lib/agent-exec-logger.mjs`
> 最後更新：2026-10-18（TASK-053 品質補強 docs 階段）

---

## 1. 概觀

本功能管理兩件事：

1. **Agent 執行軌跡** — 每次 AI agent 任務的逐步追蹤紀錄（LLM 呼叫、tool 執行、thinking、error），以及 per-Release-Unit 的 token 與成本統計。
2. **日誌保留政策** — llm / agent / other 三類日誌的保留天數設定與定時清理（purge）。

### 檔案組成

| 層 | 檔案 | 職責 |
| --- | --- | --- |
| Route | `packages/server/src/routes/agent-logs.mjs` | 6 個 HTTP 端點：列表、明細、RU 成本、RU 刪除、purge、診斷 |
| Route | `packages/server/src/routes/log-retention.mjs` | 3 個 HTTP 端點：保留設定讀寫、政策執行 purge |
| Lib | `packages/server/src/lib/agent-exec-logger.mjs` | 落盤引擎：`startAgentLog` / `listAgentTasks` / `getAgentTaskDetail` / `cleanupOldAgentLogs` / `getRuCostHistory` |
| 消費端 UI | `packages/ui/src/components/AgentLogs.tsx` | 任務軌跡檢視與 RU 成本觀測面板 |

> **⚠ 路徑澄清**：TASK-053 任務描述中的 `installed-apps/pm/ui/pages/ProjectOffice.tsx` 是 task_retrofit 自動生成時的 fileScope 誤標。該檔案與本功能無直接關係；本功能的實際後端與 UI 如上表所列。

### 日誌儲存架構

PAAW 的日誌分三層（Fleming 2026-09-06 / 2026-10-05 定調，詳見 [ADR-023](#adr-023-日誌三層架構與資產級保留政策)）：

| 目錄 | 性質 | 清理責任 | 預設保留 |
| --- | --- | --- | --- |
| `data/` | 使用者資產（備份） | 不清 | 永久 |
| `{ru}/.paaw/` | RU 版控資產 | 不清（版控） | 永久 |
| `log/logs/llm/*.jsonl` | **資產級** — LLM 呼叫記錄（成本核算） | log-retention（`llmDays`） | **永不刪**（`llmDays=0`） |
| `log/logs/agent/*.jsonl` | **資產級** — Agent 執行軌跡（ES 資料源） | log-retention（`agentDays`） | **永不刪**（`agentDays=0`） |
| `log/logs/{其他}` | 資產級非資產子目錄（cron 等） | log-retention（`otherDays`） | 7 天 |
| `log/{semgrep,app-console,versions,tmp}` | runtime 垃圾桶 | Janitor | 各自組數/份數 |

**關鍵政策**：LLM 與 agent 日誌是成本核算資產（RU 用了多少 token），預設 `days=0` 代表永不刪。

## 2. API 文件 — agent-logs 路由

Base path：`/api/agent-logs`

### 2.1 GET `/api/agent-logs` — 任務列表

列出最近的 agent 任務摘要。

**Query 參數**

| 參數 | 型別 | 預設 | 說明 |
| --- | --- | --- | --- |
| `limit` | integer | 50 | 回傳筆數上限（上限 100000） |
| `agent` | string | — | 依 agent 身分過濾（如 `coding`、`architect`、`qa`） |
| `status` | string | — | 依狀態過濾（`completed`、`interrupted`、`error`） |
| `ru` | string | — | 依 Release Unit 名稱過濾（後過濾，非 SQL 層） |

> **⚠ 已知限制（ISS-048）**：`agent` 與 `status` 同時傳送時，`status` 會靜默失效（三元互斥，只套 `agent`）。單獨使用兩者之一則正常。

**回應 — 200**

```json
{
  "items": [
    {
      "taskId": "task-1845000000-ab12cd",
      "agent": "coding",
      "status": "completed",
      "cwd": "/Users/steward/App/tPAAW",
      "ruName": "tPAAW",
      "startTime": 1845000000000,
      "durationMs": 566000,
      "usage": { "prompt": 125000, "completion": 38000 },
      "costUsd": 0.42,
      "models": [
        { "model": "claude-sonnet-4", "prompt": 100000, "completion": 30000, "costUsd": 0.35 }
      ]
    }
  ],
  "total": 1
}
```

**錯誤**

| HTTP | error 訊息 | 情境 |
| --- | --- | --- |
| 500 | `Internal error` | 讀取 index.json 失敗（不外洩內部細節） |

**回應 — 200**

### 2.4 DELETE `/api/agent-logs/ru/:ruName` — 刪除指定 RU 的所有日誌

刪除某 Release Unit 的全部 agent 任務紀錄（index 條目 + `.jsonl` 檔 + cost history 條目）。用於 RU 移機或清理。

**路徑參數**

| 參數 | 說明 |
| --- | --- |
| `ruName` | Release Unit 名稱（URL-encoded）。`-`（空白 cwd 的佔位）會被拒。 |

**回應 — 200**

```json
{ "ok": true, "deleted": 12, "ruName": "tPAAW" }
```

**錯誤**

| HTTP | error 訊息 | 情境 |
| --- | --- | --- |
| 400 | `Invalid RU name` | ruName 為空或 `-` |
| 500 | `Log index is corrupted; refusing to modify` | index.json 內容損壞 — **拒絕覆寫以保護資料完整性**（品質補強新增） |
| 500 | `Internal error` | 其他失敗 |

> **品質補強重點**：刪除前先呼叫 `readIndexEntries()` 區分「檔案不存在」（ENOENT → 當空陣列）與「內容損壞」（JSON parse 失敗 → 拒絕操作）。後者不可靜默當空陣列，否則會把整份 index 覆寫成 `[]`，造成所有任務摘要遺失。

---

### 2.5 POST `/api/agent-logs/purge` — 清理舊 agent 日誌

依天數清理 `log/logs/agent/` 下 mtime 超過保留期的 `.jsonl` 檔，並累計被刪任務的成本到 `ru-cost-history.json`（避免 purge 後成本統計遺失）。

**Request body**

```json
{ "days": 30 }
```

| 欄位 | 型別 | 預設 | 說明 |
| --- | --- | --- | --- |
| `days` | integer | 7 | 保留天數，範圍 **1–3650**。`0`（永不刪）不在此設定，請走 `PUT /api/logs/retention`。 |

> **⚠ 已知限制（ISS-045）**：此端點接受任意 `days`（1–3650），可繞過 `log-retention` 的資產政策（`agentDays=0` 永不刪）。建議搭配 `confirm` 參數或限制只能縮短保留期。

**回應 — 200**

```json
{ "ok": true, "deleted": 5, "retentionDays": 30 }
```

**錯誤**

| HTTP | error 訊息 | 情境 |
| --- | --- | --- |
| 400 | `days must be an integer between 1 and 3650` | days 非整數或超出範圍（品質補強新增） |
| 500 | `Internal error` | 清理失敗 |

---

### 2.6 GET `/api/agent-logs/ru-debug` — RU 解析診斷

診斷端點：顯示每筆 task 的 `cwd` 原始值與 `resolveRuName()` 解析結果，用於排查 RU 名稱解析錯誤。

**Query 參數**

| 參數 | 說明 |
| --- | --- |
| `test` | 直接測試任意路徑的解析結果 |
| `backfill` | `1` = 手動觸發 index.json 的 cwd 回填（機器首次啟動自救） |

**回應 — 200**：JSON 物件，含 `serverTime`、`test`（若帶 `test` 參數）、`entries`（前幾筆的 cwd 原值與解析結果）、`nullCwdCount`、`backfilled`（若觸發）。

> 此端點為維運診斷用，非正式 API 契約，回應格式可能隨診斷需求調整。

## 3. API 文件 — log-retention 路由

Base path：`/api/logs`

### 3.1 GET `/api/logs/retention` — 讀取保留設定

**回應 — 200**

```json
{
  "retention": {
    "llmDays": 0,
    "agentDays": 0,
    "otherDays": 7
  }
}
```

| 欄位 | 預設 | 說明 |
| --- | --- | --- |
| `llmDays` | 0 | LLM 呼叫記錄保留天數。`0` = 永不刪（成本核算資產） |
| `agentDays` | 0 | Agent 執行記錄保留天數。`0` = 永不刪（ES 資料源） |
| `otherDays` | 7 | 其他子目錄（cron 等）保留天數 |

---

### 3.2 PUT `/api/logs/retention` — 寫入保留設定

**Request body**

```json
{ "llmDays": 30, "agentDays": 0, "otherDays": 14 }
```

可只傳部分欄位（deep merge）。每個欄位獨立驗驗證。

**驗證規則**

| 欄位 | 合法範圍 | 錯誤訊息 |
| --- | --- | --- |
| `llmDays` / `agentDays` / `otherDays` | 整數 **1–3650** | `{key} must be 1-3650` |

> **⚠ 已知限制（ISS-045，major）**：`0`（永不刪）是預設值，但 PUT 拒收 `n < 1`。使用者一旦設過天數，就無法透過 API 回到「永不刪」。要回到 `0` 需直接編輯 `data/config/log-retention.json`。建議修法：PUT 允許 `llmDays`/`agentDays` 接受 `0`。

**回應 — 200**

```json
{ "ok": true, "retention": { "llmDays": 30, "agentDays": 0, "otherDays": 14 } }
```

**錯誤**

| HTTP | error 訊息 | 情境 |
| --- | --- | --- |
| 400 | `{key} must be 1-3650` | 欄位超出範圍（品質補強新增，與 agent-logs purge 一致） |
| 500 | `err.message` | 寫檔失敗（**⚠ ISS-047：仍外洩 err.message 含絕對路徑，同型漏修**） |

---

### 3.3 POST `/api/logs/purge` — 依政策執行清理

依目前保留設定立即清理三類日誌，並一併執行 Janitor（runtime 垃圾回收）。每日 cron `system-daily-log-purge` 也呼叫此端點。

**Request body**（可選）

```json
{ "before": "2026-01-01" }
```

| 欄位 | 說明 |
| --- | --- |
| `before` | `"YYYY-MM-DD"` — 顯式日期，刪除 LLM 日誌中檔名日期 `< before` 的全刪。優先於 `llmDays` 政策（人為主動覆蓋）。 |

**清理邏輯**

| 類別 | 條件 | 方法 |
| --- | --- | --- |
| `llm` | `before` 有值 → 依檔名日期；否則 `llmDays > 0` → 依檔名日期 | `purgeLlmBefore()` 或 `cleanupOldLogs()` |
| `agent` | `agentDays > 0` → 依 mtime | `cleanupOldAgentLogs()` |
| `other` | `otherDays` → 遞迴 mtime | `purgeOtherLogs()` + `purgeAssetOtherLogs()` |

> **⚠ 已知缺陷（ISS-044，critical）**：`runLogPurge()` 內 `const otherDeleted` 宣告後 `+=` 重賦值 → `TypeError: Assignment to constant variable`。**此端點必定 500**，每日 cron 排程清理靜默失效。修法一行：`const` → `let`（log-retention.mjs L147-150）。文件以此現狀記錄，待 developer 修復。

**回應 — 200**（ISS-044 修復後的預期形狀）

```json
{
  "ok": true,
  "retention": { "llmDays": 0, "agentDays": 0, "otherDays": 7 },
  "deleted": 3,
  "detail": { "llm": 0, "agent": 0, "other": 3 },
  "janitor": {
    "ranAt": "2026-10-18T05:00:00Z",
    "semgrepDeleted": 2,
    "appConsoleDeleted": 1,
    "versionsDeleted": 0,
    "legacyDeleted": 0,
    "tmpCleared": 5,
    "uploadsDeleted": 0
  }
}
```

**錯誤**

| HTTP | error 訊息 | 情境 |
| --- | --- | --- |
| 500 | `Assignment to constant variable` | **ISS-044** — `const otherDeleted +=`（修復前必現） |
| 500 | `err.message` | 其他失敗（**⚠ ISS-047：外洩 err.message**） |

## 4. 操作手冊

### 4.1 查詢 Agent 任務軌跡

**情境**：想看某次 agent 任務做了什麼、花了多少 token。

1. **列出最近任務**：
   ```
   GET /api/agent-logs?limit=20
   ```
   從回傳的 `items` 找到目標 `taskId`。

2. **依 agent 過濾**（例如只看 coding agent）：
   ```
   GET /api/agent-logs?agent=coding&limit=50
   ```

3. **看完整步驟明細**：
   ```
   GET /api/agent-logs/task-1845000000-ab12cd
   ```
   回傳的 `steps` 陣列包含每一步的 `phase`（`task_start`/`llm_call`/`tool_exec`/`task_end`）、耗時與 token。

4. **UI 操作**：打開 Coding IDE 側欄「Agent Logs」頁籤，直接點任務看時間線。

### 4.2 查詢 RU 成本

**情境**：想知道某個 Release Unit 總共花了多少 token 和錢。

```
GET /api/agent-logs/ru-summary
```

回傳 `rows` 依 `costUsd` 降序排列，每列含 `tasks`、`tokensIn`/`tokensOut`、`costUsd`、`durationMs` 與 `byModel` 明細。`totalCostUsd` 是全部 RU 的總成本。

> 成本統計合併 live index 與 `ru-cost-history.json`（已 purge 任務的累計），所以即使日誌被清掉，成本數字不會遺失。

### 4.3 設定日誌保留政策

**情境**：想把 LLM 日誌改為保留 90 天、其他改為 14 天。

1. **讀現況**：
   ```
   GET /api/logs/retention
   ```

2. **改設定**（部分更新，deep merge）：
   ```
   PUT /api/logs/retention
   Content-Type: application/json

   { "llmDays": 90, "otherDays": 14 }
   ```

3. **回到永不刪**（⚠ 變通）：
   - PUT 不收 `0`（ISS-045），需直接編輯檔案：
     ```
     data/config/log-retention.json
     ```
     將對應欄位改回 `0`。

> **建議**：LLM 與 agent 日誌是成本核算資產，預設 `0`（永不刪）。除非磁碟壓力大，否則不要改。

### 4.4 執行日誌清理（purge）

**情境**：設完保留天數後想立刻清，不等每日 cron。

```
POST /api/logs/purge
Content-Type: application/json

{}
```

回傳 `detail` 分別列出 llm / agent / other 各刪了幾個，外加 Janitor 的 runtime 垃圾回收報告。

**手動刪 LLM 日誌到某日期**：
```
POST /api/logs/purge
Content-Type: application/json

{ "before": "2026-01-01" }
```
這會刪除檔名日期 `< 2026-01-01` 的所有 LLM 日誌，優先於 `llmDays` 政策。

> **⚠ ISS-044**：`POST /api/logs/purge` 目前必定 500（`const otherDeleted +=`）。在 developer 修復前，每日 cron `system-daily-log-purge` 排程清理也靜默失效。暫時替代：手動刪 `log/logs/other/` 下的舊檔，或等修復。

### 4.5 清理單一 RU 的 agent 日誌

**情境**：某個 RU 不再使用，想刪掉它的所有 agent 任務紀錄。

```
DELETE /api/agent-logs/ru/old-project
```

會刪除該 RU 的：index 條目、`.jsonl` 檔、`ru-cost-history.json` 中的成本條目。

> 若 `index.json` 內容損壞，此操作會被拒（回 500 `Log index is corrupted`），以保護資料完整性。修復 index 後再重試。

### 4.6 清理 agent 日誌（指定天數）

**情境**：只想清 agent 日誌，不動 LLM 日誌，且指定天數（不用保留設定）。

```
POST /api/agent-logs/purge
Content-Type: application/json

{ "days": 30 }
```

刪除 `log/logs/agent/` 下 mtime 超過 30 天的 `.jsonl`，被刪任務的成本累計到 `ru-cost-history.json`。

### 4.7 診斷 RU 名稱解析

**情境**：任務列表裡的 `ruName` 顯示不正確（例如都顯示 `-` 或 basename）。

```
GET /api/agent-logs/ru-debug?test=/Users/steward/App/some-project
```

回傳該路徑經 `resolveRuName()` 解析的結果。解析優先序：
1. Coding app 匯入專案（`recent-projects.json`）路徑比對 → 取 folder basename
2. PAAW 自身偵測（cwd 落在 `PAAW_ROOT` 內 → `"PAAW"`）
3. Folder basename（最後手段）
4. 空白 → `"-"`

若 index.json 的 cwd 欄位空白（舊資料），可觸發回填：
```
GET /api/agent-logs/ru-debug?backfill=1
```
（server 啟動時也會自動執行一次 `backfillIndexCwd()`）

## ADR-023: 日誌三層架構與資產級保留政策

**日期**：2026-09-06（Fleming 定調）/ 2026-10-05（log 目錄統一）/ 2026-10-18（文件化）
**狀態**：Accepted（實作已完成，本文為事後補記）

### Context

PAAW 的日誌原本散落在 `data/logs/`（與使用者資產混在一起）。這造成三個問題：
1. 備份把垃圾日誌一起備份，浪費空間。
2. 日誌清理政策與使用者資產保護混在一起，容易誤刪使用者資料。
3. LLM 呼叫記錄是成本核算資產（RU 用了多少 token），但跟 runtime 垃圾（semgrep 輸出、dev console）同級，沒有區分。

### Decision

將日誌分為三層，各有明確的性質與清理責任：

1. **`data/`** — 使用者資產（對話、筆記、設定）。進備份，永不自動刪。
2. **`{ru}/.paaw/`** — RU 版控資產（feature map、issues、decisions）。版控管理，不自動刪。
3. **`log/`** — runtime 日誌根。不進備份，定時清理。細分：
   - `log/logs/llm/*.jsonl` — **資產級**，LLM 呼叫記錄，成本核算用。預設 `llmDays=0`（永不刪）。
   - `log/logs/agent/*.jsonl` — **資產級**，Agent 執行軌跡，ES 資料源。預設 `agentDays=0`（永不刪）。
   - `log/logs/{其他}` — 非資產子目錄（cron 等）。預設 `otherDays=7`。
   - `log/{semgrep,app-console,versions,tmp}` — runtime 垃圾。由 Janitor 依組數/份數清理。

**保留政策語義**：`days=0` 代表永不刪（資產級預設）；`days>0` 代表保留 N 天後刪。

**清理責任分離**：
- `log-retention` 負責 `log/logs/` 下的資產級與非資產日誌（llm/agent/other）。
- Janitor 負責 `log/` 下的 runtime 垃圾（semgrep/app-console/versions/tmp）。
- Janitor 絕不碰 `data/` 與 `{ru}/.paaw/`。

### Consequences

- **正面**：備份不再包含垃圾日誌；清理政策與資產保護職責分離；成本核算資產（LLM/agent 日誌）預設永久保留。
- **正面**：`log/` 目錄可安全地整目錄清除（除了 `log/logs/llm` 與 `log/logs/agent`），適合磁碟壓力時的應急清理。
- **負面**：`days=0` 語義與 PUT API 的 `1-3650` 驗證不一致（ISS-045），使用者無法經 API 回到永不刪。需修復 PUT 允許 `0`。
- **負面**：舊 `data/logs/` 遷移到 `log/logs/` 後，Janitor 需對 `data/logs/` 做 legacy sweep（不碰 `log/logs/`），增加邏輯複雜度。
- **中性**：成本歷史（`ru-cost-history.json`）在 purge 時累計被刪任務的成本，確保即使日誌被清，成本數字不遺失。

### Alternatives Considered

- **全部留在 `data/logs/`**：拒絕，因為備份會包含垃圾、清理政策與資產混在一起。
- **全部進資料庫**：拒絕，JSONL 檔案符合 ADR-001（file-based knowledge store），且可直接被 Elasticsearch shipper 消費。
- **LLM 日誌也定時刪**：拒絕，LLM 日誌是成本核算資產，刪了無法回溯歷史成本。
